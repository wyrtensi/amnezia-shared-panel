# Optional AWG 3.1 Node Bridges Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans or superpowers:subagent-driven-development to implement this plan task by task.

**Goal:** Manage bridges and VPN nodes in one panel, let administrators select the AWG 3.1 entry point per node, and preserve the existing user download and config refresh flow.

**Baseline:** `main` at `2d67f2936f126788be69d27b27045fec34649e1b`. The baseline includes the merged AWG client profile and external reachability changes. Use its Node 24 toolchain.

**Spec:** [Design and acceptance criteria](#design-and-acceptance-criteria).

**First-release scope.** The operator chose one generated frpc setup command per node and bridge pairing. After that command the panel verifies and activates the route. Bridge agents are independently managed from the panel and CLI, including version discovery, explicit updates and update status.

## Design and acceptance criteria

**Administration.** Register multiple bridges in one panel. A bridge has a name, a public IPv4 address, a frps control TCP port and an allowed UDP port range. Configure each bridge host once. In Policies → Node routes choose Direct or an existing bridge for the selected VPN node. The panel reserves the first free UDP port in its range and shows the setup for that node. The administrator can override the suggestion with a free port. Activate the candidate after validation. Several nodes can use the same bridge on separate ports. Each node uses one active bridge at a time. The bridge list shows its routes, reserved ports and remaining capacity. One panel owns the bridge enrollment and port pool in the first release.

**User flow.** New and existing keys use the node's current assignment when the panel delivers a config. Switching Direct → Bridge → Direct takes effect on the next export of the same key. The existing Refresh config action still refreshes the AWG 3.1 client profile, then opens the existing delivery dialog. Any resulting download uses the assignment current when the export request reads the database. Repeat downloads use the current assignment as well. The user imports the replacement in the client. A previously imported file continues to use the endpoint it contained at import time.

**Transport.** Run one `frps` service per bridge and one `frpc` service per node and bridge pairing. Every public UDP port maps to one node's AWG 3.1 listener. The AWG peer and exit stay on that node. The administrator runs the host setup instructions shown by the panel. The panel stores connection metadata and manages assignment. The existing node-agent API path uses its management address.

**Setup flow.** Create bridge → install `frps` and `bridge-agent` once and enroll the bridge → add a node route → install or extend that node's `frpc` → verify → activate. For a second node on the same bridge, reuse the existing `frps`, firewall range and trust material. The panel displays the selected bridge, reserved public UDP port, local AWG destination and one copyable setup command per host action. The host-side scripts support a dry run and keep the existing AWG and node-agent services running.

**Port lifecycle.** A draft holds its port while setup and validation run. Activating a replacement or selecting Direct moves the old route to Retiring. Already imported files can still use that forwarding path during the transition. Release its port after a fresh bridge observation confirms the specific forwarding registration is gone and the operator confirms that the migration window has ended. An unknown bridge state keeps the reservation. Removing a bridge or VPN node requires clearing its draft, active and retiring routes first. Use restrictive foreign keys. The existing force-delete option for VPN keys does not override the route guard.

**Scope.** A bridge assignment applies to the node's genuine AWG 3.1 artifacts. Native AWG 2 and an AWG3 service's 2.0 fallback keep their current direct path. Label this in the admin control. New user exports follow the node policy without an additional user choice. Multiple registered bridges allow manual reassignment in admin settings. Automatic failover of an imported client and cross-node peer replication are separate features.

**Approaches.** A user-facing Direct/Bridge selector would give each user control and would require another choice on every export. Storing the bridge in each encrypted artifact would require a bulk rewrite or reissue when an admin changes the assignment. The proposed node-level assignment with export-time rendering applies the admin's choice uniformly and keeps current credentials available through the existing flow.

**Blocked-only keys.** `ru_blacklist` keeps the existing file-only behavior. Offer `.vpn` and `.conf` under current policy. The bridge changes the endpoint for packets routed into the tunnel. `AllowedIPs`, configured DNS, split-route merges, route budgets and empty/oversized fallback follow the existing exporter. Full-tunnel link, file and QR exports use the same bridge endpoint.

## Managed infrastructure nodes

Rename the admin navigation item VPN nodes to Nodes and bridges (Ноды и мосты). Keep `/admin/nodes` as its address. Within it, use separate Nodes and Bridges tabs, defaulting to Nodes. The Bridges view has a stable deep link for the overview and route-policy navigation. Both resource types use the same admin infrastructure view. A VPN node runs `node-agent`, owns peers and issues VPN keys. A bridge runs `bridge-agent` and `frps`, reports its UDP forwarding registrations, and can serve multiple VPN nodes. The Control API exposes a typed `kind: "vpn" | "bridge"` union in the shared admin view. Policies → Node routes is the only editor for active bridge assignments. Node and bridge cards link to that editor and show the current route. Store bridge records separately in `vpn_bridges`. Existing VPN tables drive key issuance, peer reconciliation and service-key provisioning. Keep these consumers scoped to VPN nodes.

### Panel connection and bridge-agent scope

- Install frps and bridge-agent together on the bridge host. Assign the bridge its own stable ID at enrollment. Use the existing private management pattern. Bind the agent to loopback and use an authenticated SSH forwarding path with a pinned host key. Reuse the allocator for panel-side tunnel ports. The panel's deployment configuration constrains allowed management destinations to the trusted tunnel endpoints.
- Give the bridge a distinct management credential, stored encrypted in the panel, separate from the frp token and local dashboard credential. Keep the frps dashboard on loopback. Public VPN UDP and the trusted-source frpc control TCP listener retain their own ports.
- Define a versioned authenticated `GET /v1/status` for the bridge agent. Return the stable bridge ID, agent version, frps status and version, applied control port and UDP range, and the selected forwarding fields `proxyId`, `remotePort`, `online` and a registration marker derived from the pinned frps response's `clientID` and `lastStartTime`. Return bounded structured errors. Store the panel's last observation timestamp. The agent reads the pinned frps release's local status endpoints. Its versioned management API exposes status, identity and the narrowly scoped agent update operations.
- Derive the proxy name from the reserved route UUID. Match both that name and public UDP port against the route in the panel. The current shared bridge credential authenticates the trusted frpc group. A proxy name and live registration show which port frps reports. Bind the AWG verification to the observed registration marker. The actual handshake with the assigned node's peer verifies the destination. A changed or unavailable marker requires fresh verification. The marker describes the observed frps registration.
- Keep separate states for management availability, frpc registration and end-to-end AWG. A missing or stale bridge observation is Unknown. Losing the management channel leaves existing active assignments and forwarding in place. Activation checks the latest stored fresh online registration and a recent AWG check or operator verification for that same registration. Compare the observed marker and the expected node revision within the activation transaction.

The installer and applier can share validation and the per-route service naming. Before adding remote apply, verify per-node authorization on the frp side and design separate credential enrollment. The operation is limited to the specific frpc service and its configuration.

### Independent bridge-agent updates

Publish bridge-agent as its own versioned OCI image. Install it as a dedicated Compose service with a loopback management listener. frps runs as a separate host service and owns the UDP forwarding ports. The bridge host keeps the enrolled identity, credentials, applied route registrations and updater state across agent replacement.

The bridge card in Nodes and bridges → Bridges shows installed version, an available approved image and the last update result. The administrator previews and confirms one bridge update. CLI commands `bridge-agent-update <bridge-id> [--confirm]` and `bridge-agent-log <bridge-id>` use the same Control API. Updates use a digest from the approved bridge-agent repository. Track frps version separately in the bridge status.

The Control API queues a bridge update intent with a stable operation ID. A worker sends it through the private bridge API. The agent writes a bounded request to its dedicated spool. The host's systemd updater independently validates the repository, digest and operation ID, stages the candidate while retaining the current image and config, and recreates only the bridge-agent service with `--no-deps`. The agent exposes typed status and update endpoints. The host updater owns Docker access.

The health gate verifies the candidate digest, expected bridge identity and a successful authenticated status response from the new agent with a compatible local frps read. On failure restore the previous image and verify it independently. Report a confirmed rollback and a failed rollback as separate outcomes. Track lost management contact as an observation until the host reports a matching terminal result. Persist the operation and rollback state across service restarts or timeouts. Replaying an operation ID returns its known state and preserves at-most-once apply semantics.

The update targets the management agent. Updating the frps forwarding service is a separately scheduled operation. Test that active routes remain in service during bridge-agent update and rollback.

## Port mapping and fleet preflight

The existing AWG node listener is the last hop. frpc runs as a host service and forwards to that host's existing published AWG UDP port. A default installation uses `127.0.0.1:51890/udp` as the target. On November 13, a read-only Control API and Docker audit of the six enabled amster3 nodes confirmed `51890/udp → 51890/udp` published on all IPv4 and IPv6 host addresses. All six AWG3 containers reported healthy. Caminia was outside the node audit. This confirms the host mappings. A handshake through the future bridge is the acceptance test for the full path.

| Where | Purpose | Suggested value | Check |
| --- | --- | --- | --- |
| AWG node host | Existing local UDP destination for frpc | `127.0.0.1:51890/udp` on a wildcard or loopback IPv4 publication | Inspect Docker's actual UDP port mappings and AWG3 health. |
| Bridge host | frpc control and transport connection | `7000/tcp` | Confirm a free TCP bind and an allowed outbound connection from each node. Restrict the bridge-side firewall rule to the trusted node source addresses. |
| Bridge host | Public entry for users' AWG datagrams | Inclusive UDP pool `41000–41031`, one reserved port per route | Check existing UDP listeners, host and provider firewall rules, and successful frps registration. |
| User config | The effective AWG peer endpoint | `<bridge-ip>:<reserved-udp-port>` | Verify the client handshake and an HTTP request through the tunnel. |

For example, on the same bridge, Node A uses external `41000/udp` and Node B uses `41001/udp`. Both frpc processes can forward to `127.0.0.1:51890/udp` because each runs on its own host. Keep the current AWG publication and the existing management API ports. The suggested bridge pool contains 32 ports. The bridge card counts draft, active and retiring reservations against that capacity. Admins may pick a different unused TCP port or UDP pool before installing a new bridge.

**Port compatibility check.** The suggested pool is the initial operating default. The administrator may choose `443/tcp` for the frpc control connection if the bridge can bind it and the nodes' egress policies require it. For client traffic, test `443/udp` against one pool port only on an isolated test bridge when that port is free. Use the same bridge IP, AWG node, client profile and user network. Compare handshake and HTTP success before changing a default. Port choice changes reachability conditions while the client still sends AWG packets. The test can use temporary lab forwarding rules outside the panel allocator.

**Port detection.** The node-side helper reads `docker port amnezia-awg3` and health from Docker. Accept a single matching IPv4 UDP publication for the AWG3 listener and use its host port. A wildcard or loopback publication allows the loopback destination. If the only publication is on a specific local IPv4 address, require an explicit local target matching that binding. A missing, ambiguous or IPv6-only publication stops setup with the observed mapping and expected input. Keep that decision on the node host. A different host port is an input to frpc.

**Firewall verification.** One bridge installation sets the frps port allowlist to the registered UDP pool. Host and cloud firewall rules follow that pool for client UDP and the separate trusted-source rule for control TCP. The host preflight checks local binds. An authenticated frpc connection from the actual node checks the control path. A genuine AWG handshake and HTTP through the candidate UDP port check the public path. A successful TCP connection or a silent UDP packet alone provides no VPN verdict.

## Operator setup in the panel

1. **Add bridge.** Ask for the name and public IPv4. Put control TCP port and UDP pool under advanced settings with the defaults above. Show how many routes fit. Generate a host setup command and a dry-run variant using only these fields and the bridge ID.
2. **Install the bridge once.** The operator runs the frps and bridge-agent installer and applies or verifies provider firewall rules. The installer validates both services and confirms the control listener. It keeps the frp token and TLS private key material on the host. Register the private management endpoint in the panel and verify the bridge identity. Route readiness comes from registration and candidate checks.
3. **Prepare a node.** Choose a bridge for the VPN node in Policies → Node routes. The panel reserves a port in a transaction and shows the public entry and the default local target. The node helper reports the actual local destination. Copy the frpc setup command to the node host. The helper detects the local port and accepts an explicit checked override. For a second node, repeat this step without restarting frps.
4. **Verify and activate.** Show fresh registration from bridge-agent and the result of the external AWG check. The admin activates the verified candidate with the current assignment revision. Existing users can use the usual download or Refresh config flow to get that entry point. Selecting Direct produces the original endpoint on the next download.
5. **Retire.** Show the old port and keep forwarding while previously imported files are in use. After the transition, provide the removal command for the specific frpc unit and release that port only after confirmation. Apply the same cleanup to a canceled draft that was already installed.

**Installer interfaces to implement.** Use `infra/bridge/install-frps.sh --bridge-id <id> --control-port <tcp> --udp-start <first> --udp-end <last> [--dry-run]` and `infra/node/scripts/install-frpc.sh --route-id <id> --bridge-ip <ip> --control-port <tcp> --public-port <udp> [--local-udp-port <udp>] [--local-ip <ip>] [--dry-run]`. The panel exposes the suggested commands as text in the admin flow and CLI. The operator transfers the bridge token and CA using an authenticated channel into protected local files. Keep credentials out of command arguments. A dry run reads actual listeners, mappings and existing unit names and reports planned changes. An installer run validates inputs and config before writing or starting its own unit. A repeat with the same inputs succeeds without a new route. A conflict with an existing unit or mapping stops with the conflicting field.

**Failure messages.** Distinguish an exhausted bridge pool, a port already held by a route, a missing local AWG publication, failure to reach control TCP, frp authentication or TLS failure, frps UDP registration failure, and no AWG handshake from the probe network. If the UDP test cannot identify the failing hop, show the result as a failed path check and retain the evidence from each step. The active assignment changes only after successful validation and explicit activation.

## Implementation details

### Control API and persistence

Use the existing admin authentication and response patterns in `apps/control-api/src/app.ts`, `service.ts` and `postgresRepository.ts`. Define the request and response schemas in `packages/contracts/src/index.ts`. Read models carry status and observations. Credential inputs travel through the authenticated write endpoint and are encrypted before persistence.

| Operation | API and expected behavior |
| --- | --- |
| Infrastructure read | `GET /api/admin/infrastructure` returns the typed VPN and bridge rows. Add an optional bridge summary to `GET /api/admin/overview`, based on the same saved observations. Existing VPN endpoints remain available to their callers. |
| Register bridge | `POST /api/admin/vpn-bridges` accepts `{ name, publicIpv4, controlTcpPort, udpPortStart, udpPortEnd }` and returns its ID and normalized port settings. The new record is pending enrollment. A second record for the same public IPv4 conflicts. |

### Route states and recovery

| Trigger | Persisted result | Endpoint on the next normal export |
| --- | --- | --- |
| Register a bridge or prepare a draft | Bridge or draft exists and any chosen port is reserved. | Existing active assignment, or Direct. |
| frpc registers and candidate verification succeeds | Store method, registration marker and check time on that route. | Existing active assignment, or Direct. |
| Activate verified route at expected revision | Draft becomes Active. Any previous active route becomes Retiring. Increment node endpoint revision. | The new bridge endpoint. |
| Select Direct at expected revision | Previous route becomes Retiring. Increment node endpoint revision. | The original endpoint in the saved artifact. |
| Bridge status is lost or the candidate check fails | Record the observation. Keep the held port and the active route. | Existing active assignment, or Direct. |
| End migration and remove old forwarding | After confirmed removal and a fresh observation, release the retiring route's port. | Existing active assignment, or Direct. |

A reconnect or a changed observed registration invalidates verification. Compare the marker again at activation. A test export changes only the draft endpoint in the downloaded file and does not mark ordinary rules as delivered. A downloaded config carries the endpoint selected for that response. Already imported files keep that endpoint while their forwarding exists.
